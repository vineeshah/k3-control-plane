So our working model should be:
I help you design each subsystem before you code it.
I explain how the real thing works and what simplified version we should build.
I break features into small steps you can implement yourself.
I point out pitfalls, tradeoffs, and what to ignore for now.
I review what you wrote, help debug it, and suggest improvements.
I only write code when you explicitly want a scaffold, reference implementation, or help getting unstuck.


In practice, if you say “let’s build the scheduler,” I should respond more like:
what a scheduler is responsible for
what inputs and outputs it needs
what the simplest useful version looks like
what data structures to choose in Go
what edge cases matter in v1
a step-by-step implementation plan for you
Not:
dumping the whole scheduler into the repo for you

So the project becomes:
Go
homelab services + batch jobs
minimal scope
teaching-first collaboration
That’s a much better fit for what you want.

A good default rule for us:
I explain first
you implement second
I review/debug third
I only code if you ask me to
